# Local editor v3.0 — hybrid Russian GEC

## Why v2.x was a dead end

The previous service asked one generative model to discover and express edits, then
tried to rescue the result with increasingly narrow filters. Production logs showed
that A/B/C produced different valid-looking inflections instead of a stable edit
set. The fundamental problem was candidate generation, not prompt wording.

## v3 design

The service is now split into four stages:

1. **Context-first generation**. The model sees the selected text plus a larger
   LibreOffice context. It generates a corrected text draft rather than pretending
   to know that each word can be evaluated independently.
2. **Diff-to-edits**. The server converts the draft into bounded local edits. Whole
   paragraph rewrites, paragraph reflow, newline changes and large replacements are
   rejected before they reach the decision engine.
3. **Independent adjudication**. A second model receives the original sentence and
   only the extracted local candidates. It may reject a candidate, but it cannot
   invent a replacement. A transport/JSON failure is not treated as a semantic
   rejection.
4. **Deterministic structural gate**. DecisionEngine checks exact occurrence,
   overlap, protected terms, morphology-risk, word-boundary changes and limits.
   Natasha/pymorphy3 provides a separate dependency-aware agreement candidate
   source. LanguageTool is an optional verifier only; it is never the main detector.

## Why this architecture is different

Russian GEC research increasingly separates edit generation from full sequence
rewriting. The 2025 Russian sequence-tagging work reports gains from language-
specific edit operations, while the LORuGEC work shows that targeted similar-example
retrieval materially improves few-shot LLM GEC. v3 combines these ideas with a
modern local LLM only where generation/reasoning is useful, while preserving a strict
server-side edit contract.

Qwen3.5-4B is used only as an experiment because its current model card supports
explicit thinking configurations and a current Transformers implementation. The
experimental backend is lazy-loaded and never creates a second HTTP server.

## LanguageTool decision

LanguageTool is intentionally not the candidate source. It is exposed through a
small HTTP verifier adapter because its rule matches are useful as an independent
negative signal after a candidate has already been generated by a context-aware
model or dependency parser.

## Operational rule

There remains exactly one `ai-suggester.service` and one uvicorn process on port 8000.
Only `.env` selects the preset. Do not start a second uvicorn or a second production
service.
