# Тюнинг производительности локального корректора

Документ привязан к конкретному серверу, на котором развёрнута служба, и
объясняет не только «что поставить», но и почему.

## 1. Что за железо

```
Astra Linux 1.8 (x86-64), ядро 6.1.158-1-generic, гипервизор VMware
2 × Intel Xeon E5-2690 v4 @ 2.60 GHz — 16 ядер на сокет, 32 vCPU, HT выключен
NUMA: node0 = CPU 0-15, node1 = CPU 16-31
L3 = 2 × 35 MiB, RAM 31 GiB (доступно ~27 GiB), swap 1 GiB
```

Существенные для инференса свойства:

* **Broadwell.** Есть AVX2 и FMA, **нет AVX-512, нет bf16, нет AMX.**
  Поэтому `bfloat16` для torch бесполезен (эмуляция медленнее fp32), а
  выигрыш даёт int8 через VNNI-независимый `fbgemm`-путь или GGUF Q4 в
  llama.cpp, собранный с AVX2.
* **Две NUMA-зоны.** Для мелких моделей на CPU основной источник разброса
  latency — межсокетные обращения к памяти. Поток, запущенный на node0, но
  читающий веса из памяти node1, теряет заметную долю пропускной
  способности.
* **32 vCPU при одном пользовательском запросе за раз.** Расширять
  параллелизм внутри одной модели после ~8–16 потоков бессмысленно:
  синхронизация начинает доминировать.

## 2. Разделение по NUMA

Две прожорливые части — Python/torch (SAGE) и Ollama (Qwen3.5-GEC,
T-lite/GigaChat) — разводятся по узлам.

`ai-suggester.service` (в репозитории уже настроен):

```ini
AllowedCPUs=0-15
Environment="MALLOC_ARENA_MAX=2"
Environment="OMP_NUM_THREADS=8"
```

Ollama — на второй узел:

```bash
sudo systemctl edit ollama.service
```

```ini
[Service]
AllowedCPUs=16-31
Environment="OLLAMA_NUM_PARALLEL=1"
Environment="OLLAMA_MAX_LOADED_MODELS=2"
Environment="OLLAMA_KEEP_ALIVE=30m"
Environment="OLLAMA_KV_CACHE_TYPE=q8_0"
```

Пояснения:

* `OLLAMA_NUM_PARALLEL=1` — служба обслуживает по одному запросу
  пользователя; параллельные слоты только делят одни и те же ядра и
  раздувают KV-кэш;
* `OLLAMA_MAX_LOADED_MODELS=2` — одновременно нужны GEC-специалист и одна
  rescue-модель, больше держать в памяти незачем;
* `OLLAMA_KV_CACHE_TYPE=q8_0` сокращает KV-кэш примерно вдвое при
  незаметной на коротких фрагментах разнице в качестве;
* `AllowedCPUs` требует cgroup v2 (в Astra 1.8 включён по умолчанию).
  Альтернатива для ручного запуска — `numactl --cpunodebind=1 --membind=1`.

Проверка раскладки:

```bash
systemctl show ai-suggester.service -p AllowedCPUs
systemctl show ollama.service -p AllowedCPUs
numastat -p "$(pgrep -f 'uvicorn decision_app')"
```

## 3. Потоки torch для SAGE

`SAGE_CORRECTOR_THREADS=2` из v8 — прямая причина 1.2–2.7 с на фрагмент
в 200 символов из журналов. На выделенном узле разумный диапазон 8–16;
значение по умолчанию в v9 — `8`.

```env
SAGE_CORRECTOR_THREADS=8
SAGE_CORRECTOR_MAX_BATCH=8
```

Число потоков torch фиксируется при первой загрузке модели и после этого
не меняется, поэтому правка требует перезапуска службы.

## 4. int8-квантизация SAGE

```env
SAGE_QUANTIZE=int8
```

`torch.ao.quantization.quantize_dynamic` по `nn.Linear` для
encoder-decoder на 95 М параметров на CPU обычно даёт кратное ускорение
при неизменном выводе на коротких предложениях. Флаг по умолчанию
выключен: включайте после прогона

```bash
PYTHONPATH=..:. python -m eval.run_eval --stack full
```

и сравнения метрик с fp32. Если `error_exact` просел — вернитесь на
`none`. Это ровно тот случай, когда решение принимается по метрике, а не
по ощущению.

## 5. Сегментация как средство ускорения

v9 отправляет в модели отдельные предложения, а не весь фрагмент.
Внимание квадратично по длине, поэтому пять предложений по 60 токенов
считаются быстрее одного на 300 токенов, при этом SAGE обучался на
одиночных предложениях и на них точнее. Ограничение — `LOCAL_MAX_SENTENCES`
(по умолчанию 12), защита от вставки пользователем целой страницы.

## 6. Сокращение работы моделей

Порядок стадий в v9 устроен так, что дорогие модели не запускаются
напрасно:

* детерминированные правила и словарная орфография — микросекунды и
  единицы миллисекунд;
* SAGE и GEC-специалист — всегда, параллельно, по предложениям;
* rescue (T-lite 8B / GigaChat 10B-A1.8B) — только при `LOCAL_RESCUE_MODE=auto`
  и отсутствии подтверждённых кандидатов.

Для максимальной скорости на слабой нагрузке:

```env
LLM_PRESET=X          # без rescue, Ollama не обязателен
LOCAL_RESCUE_MODE=never
```

Для максимальной полноты:

```env
LLM_PRESET=Y
LOCAL_RESCUE_MODE=auto
```

Из rescue-моделей на этом CPU предпочтительна **GigaChat3.1-10B-A1.8B**
(MoE, 1.8 B активных параметров на токен): при сопоставимом качестве она
считает существенно меньше FLOPs на токен, чем dense-модель T-lite 8B.
Это preset `B`.

## 7. Прогрев и keep-alive

Холодный старт — 25–30 с (загрузка SAGE и первый вызов GEC). Поэтому:

```ini
TimeoutStartSec=180
```

```env
OLLAMA_WARMUP=true
OLLAMA_KEEP_ALIVE=30m
```

Без `keep_alive` Ollama выгружает модель, и первый запрос после паузы
платит полную стоимость загрузки GGUF с диска.

## 8. Наблюдаемость

```bash
curl -s localhost:8000/metrics | python3 -m json.tool
```

Полезные поля:

* `stage_calls` / `stage_ms` — сколько раз и сколько миллисекунд
  потратила каждая стадия. Если `gec` равен нулю при непустом тексте —
  специалист не вызывается, и это дефект конфигурации (в v8 так было
  всегда из-за grammar gate);
* `guard_rejections` — по каким причинам отклонялись правки моделей;
  рост «лексическая подмена словарного слова» означает, что модель
  галлюцинирует и стоит понизить её вес или сменить;
* `degraded` — стадии, упавшие на прогреве или в рантайме.

## 9. Чего делать не нужно

* **Не поднимать `OLLAMA_NUM_PARALLEL`** ради «запаса»: на CPU это
  замедляет единственный активный запрос.
* **Не включать `bfloat16`** для torch: на Broadwell нет нативной
  поддержки.
* **Не расширять `NUM_THREADS` до 32.** Потоки одной модели начнут
  конкурировать между сокетами, а вторая часть стека останется без ядер.
* **Не отправлять текст в api.languagetool.org.** Служебные документы не
  должны покидать сервер; LanguageTool разворачивается локально на 8081.
