# Журнал v1.6 — Retrieval-augmented few-shot для русского GEC

## Контекст

После ряда серверных фиксов v1.5.8–v1.5.11 (терминатор `===END===`, фильтр
«…»-цитат, валидация «было», реконструкция CHANGES из diff) оставалась
корневая проблема: **ни одна из 11 моделей пула не справляется с
структурной пунктуацией длинных юридических конструкций** (эталонный
текст Росгвардии, 4 известные ошибки обособления — 0-2 из 4 находятся).

Первоначальная гипотеза (см. `АНАЛИЗ_МОДЕЛЕЙ_2026_05.md`): перейти
на специализированный GEC-корректор — SAGE FRED-T5 от ai-forever.

**PoC опроверг гипотезу.** На тексте Росгвардии (30 апреля 2026):

| Модель | Латентность | Запятые найдены | Галлюцинации |
|---|---|---|---|
| `sage-fredt5-distilled-95m` (95M) | 3.2 с | 0 / 3 | «2025» → «2015», пустая «» |
| `sage-fredt5-large` (1.7B) | 22.5 с | 0 / 3 | «2025» → «2015», «ТопСервис» → «Топ-Сервис» |
| `sage-mt5-large` (1.2B) | 49 с | 0 / 3 | «2025» → «2015» |
| `sage-m2m100-1.2B` (1.2B) | 46.5 с | 0 / 3 | — (но и правок нет) |

Выводы:
1. SAGE обучена на типо- и орфо-ошибках из Wikipedia/видео-транскриптов,
   а не на структурную пунктуацию обособления. Другая задача.
2. SAGE стабильно галлюцинирует числа («2025 год» → «2015 год»).
   Для юр.документа — критичная ошибка.
3. F1 paper-метрик (60 %) получены на RUSpellRU, а не на нашем домене.
   Academic benchmark ≠ prod.

## Новая гипотеза (v1.6)

Проверил Sorokin & Nasyrova (BEA @ ACL 2025, LORuGEC paper). Их
эмпирические цифры на русском GEC:
- 0-shot LLM (T-lite / YandexGPT): **~55 % F0.5** (то что у нас сейчас)
- 5-shot LLM + GECToR retrieval: **83 % F0.5 — SOTA**
- Fine-tune seq2seq: 65–75 % F0.5 (хуже retrieval-augmented)

Retrieval лучше fine-tune. Ещё и почти бесплатно.

## Архитектура v1.6 Этап 1 (реализована)

```
ПОТОК:
    request (raw_text + context)
        ↓
    _rag_context(raw_text)           # старый RAG, без изменений
        ↓
    [NEW] _gec_bank.search(raw_text, top_k=3)  # FAISS-like в numpy
        ↓ [top-3 похожих пар из банка]
    [NEW] build_few_shot_messages(   # system + N × (user, assistant) + user
              SYSTEM_PROMPT, user_msg, examples
          )
        ↓
    call_ollama(messages)            # тот же T-lite-it-2.1
        ↓
    ===CORRECTED=== / ===CHANGES===  # тот же формат
        ↓
    _drop_idempotent_changes  ← оставили 1.5.11 как есть
    _drop_changes_not_in_text ← оставили 1.5.11 как есть
    _rebuild_changes_from_diff ← оставили 1.5.11 как есть
        ↓
    client
```

### Эмбеддер

Переиспользуем RAG-эмбеддер (если `RAG_ENABLED=true`) — один
`OllamaEmbedder(nomic-embed-text)` на оба индекса. Если RAG выключен,

качество ниже, но сервер не ломается).

## Источник seed-банка и лицензирование

- Данные: LORuGEC (Sorokin & Nasyrova 2025, BEA @ ACL 2025),
  https://github.com/ReginaNasyrova/LORuGEC
- Формат исходника: XLSX, 961 строка, 48 правил,
  колонки «Initial sentence» / «Correct sentence» / «The rule» / …
- Обработка (см. `/tmp/build_seed_bank.py`, коммитить не нужно):
  - оставлены только пары, где `Are both sentences the same? == No`
  - детокенизация (убран пробел перед пунктуацией)
  - баланс `≤ 6 пар на правило` (чтобы банк не был перекошен)
  - 288 пар на выходе
- Цитирование обязательно (описано в `.env.example` и docstring модуля).

3. **Бенчмарк на LORuGEC-test (1945 пар)** — скрипт отдельно, не

   ~55 % в 0-shot).
4. **Проверка на Росгвардии с USE_FEW_SHOT=true** — требует реального
   Ollama на прод-машине, делается после мержа PR.

## Ожидаемые acceptance criteria

На момент релиза (acceptance на проде):

1. `USE_FEW_SHOT=false` — **побайтово** то же поведение, что в v1.5.11.
   Гарантируется: код пути few-shot изолирован, `messages` строится
   старой веткой.
2. `USE_FEW_SHOT=true` — на тексте Росгвардии: **≥ 3 из 4**
   эталонных запятых обособления находятся. (Сейчас 0–2.)
3. Warm-латентность — без регрессий. 3 примера × ~150 токенов =
   +450 tokens в промпте → при `num_ctx=2048` запас остаётся,
   `num_predict` не меняется, ожидаем +3…5 с к warm (45 → 48–50 с).
4. Формат `===CORRECTED===/===CHANGES===/===END===` — стабилен.
   Каждый из 3 assistant-примеров в истории демонстрирует правильный
   формат, модель имитирует.
5. Никаких новых галлюцинаций. Все предыдущие защиты
   (`_drop_changes_not_in_text`, `_rebuild_changes_from_diff`) активны.

# Журнал v1.6.1 (5 мая 2026) — диагностика NUMA + расширение GEC-банка

## NUMA-фикс (главная победа сессии)

При тестировании 8B (`t-tech/T-lite-it-2.1`) и 4B (`Vikhrmodels/QVikhr-3-4B`)
на прод-сервере latency была катастрофической — простое `ollama run "Привет"`
занимало **1м37с** на 4B-модели, а `/suggest` упирался в таймауты 300-900 с
даже при 0-shot.

`ollama run --verbose` показал:
- `prompt eval rate`: **0.66 tok/s** (ожидаемо: 30-60)
- `eval rate`: **0.07 tok/s** (ожидаемо: 5-7)

Корень: VMware-виртуалка с 2 NUMA-нодами по 16 ядер/16 ГБ; Ollama в systemd
запущена через `numactl --cpunodebind=0 --membind=0` — половина железа
отрезана, плюс жёсткий NUMA-bind в гостевой ОС конфликтует с расписанием
vCPU гипервизором.

**Фикс — заменить `/etc/systemd/system/ollama.service.d/override.conf`:**

```ini
[Service]
ExecStart=
ExecStart=/usr/local/bin/ollama serve
Environment="OLLAMA_KEEP_ALIVE=24h"
Environment="OLLAMA_NUM_PARALLEL=1"
```

```bash
sudo systemctl daemon-reload
sudo systemctl restart ollama
```

После фикса:
- `prompt eval rate` 0.66 → **58 tok/s** (88×)
- `eval rate` 0.07 → **5.29 tok/s** (75×, для 4B); 9.22 tok/s для 8B
- `ollama run "Привет"` 113 с → **1.79 с**

## Latency после фикса (T-lite 8B + retrieval)

|---|---|---|
| 0-shot | 74 с | 4/4 (2 точно + 2 валидной альтернативой) |
| 1-shot (top_k=1) | 75 с | 4/4 |
| 3-shot (top_k=3) | — | не тестировали (1-shot достаточно) |

**Цель «70-80 с с лучшим качеством» достигнута на T-lite 8B без llama.cpp.**

## Расширение GEC-банка

Существующий `gec_bank.jsonl` — 288 пар (по 6 примеров на правило × 48 правил).
В тесте Росгвардии retrieval не находил релевантных пар на ошибку
`должностного лиц → должностных лиц` (Grammar/число), потому что в банке
было только 24 grammar-пары на 4 правила.

**Расширение через `tools/build_gec_bank/build.py`:** парсим
полный LORuGEC.xlsx (960 пар) → `gec_bank_extended.jsonl` (639 новых пар,
не пересекаются с базовым банком). Итого после подключения двух файлов:

| Раздел | Базовый | Расширенный | Итого |
|---|---|---|---|
| Spelling | 150 | 317 | 467 |
| Punctuation | 102 | 235 | 337 |
| Grammar | 24 | 55 | 79 |
| Semantics | 12 | 32 | 44 |
| **Всего** | **288** | **639** | **927** |

**Latency-импакт расширения банка: 0%.** Размер банка не влияет на /suggest
runtime — мы достаём top_k (=1) ближайших примеров из любого по размеру
пула. Изменяется только время первичной индексации (linear по объёму, потом
disk-cache из v1.6.0).

## v1.6.3 — Конфигурируемый эмбеддер для GEC-банка

Phase 2 в виде маленького аддона: новая переменная `GEC_EMBED_MODEL`,
по умолчанию равна `RAG_EMBED_MODEL` (т.е. `nomic-embed-text`). Идея —
позволить администратору безопасно тестировать другой эмбеддер на
GEC-банке, не трогая RAG-документы (для длинных регламентов nomic был
выбран осознанно по объёму контекста, и менять его на каждой итерации
не хочется).

Fingerprint кэша индекса включает имя эмбеддера → автоматическая
переиндексация при смене модели; старый кэш остаётся на диске, и
откат — это снять переменную и рестартнуть.

Подкреплено документацией в `.env.example` и обновлёнными тестами
`test_gec_bank.py`.

## v1.6.7 — Гибридный retrieval (BM25 + dense, RRF) + анти-галлюцинационный SYSTEM_PROMPT

**Контекст.** Прод-тест 5 мая 2026 на втором, более длинном
административном тексте (контракт КС-2, сметы) показал регресс
качества при той же конфигурации (T-lite-it-2.1:q4_K_M, USE_FEW_SHOT=true,
GEC_TOP_K=1, GEC_EMBED_MODEL=bge-m3, банк 894 пары):

- **Найдено эталонных правок: 1 / 4** (вместо 4/4 на предыдущем тесте).
- **+2 галлюцинации:** `Проведенными → Проведёнными` (е/ё стилистика, не
  ошибка) и `Подразделения → Подразделению` (модель «улучшила»
  грамматически правильное слово).
- Few-shot retrieval подмешал нерелевантную пару `Запятая перед
  союзом «как»` вместо нужных `Согласование причастий` /
  `Согласование числа существительных` — пары с такими правилами
  в банке есть (76 шт.), но bge-m3 их не выбирает на длинном входе
  с предметной лексикой (КС-2, государственный контракт, млн рублей).

**Корневая причина** (Sorokin & Nasyrova, BEA @ ACL 2025, та же группа,
что собирала LORuGEC): *«similarity between input texts does not
necessarily correspond to similar grammatical error patterns»*. На
длинных официальных текстах семантическое сходство (которое и
оптимизирует dense embedder) уводит ранжирование от грамматического
сигнала. Их рецепт — заменить dense на edit-based encoder (GECToR-like).
Альтернатива от Tang et al. (NAACL 2024) — двухстадийный retrieval:
BM25 для отбора кандидатов, синтаксический re-rank для финального
выбора. Производственная практика 2026 (tim-ponomarev/hybrid-rag,
legaltech RU): RRF dense+sparse даёт +27 % nDCG@10 на правовом домене.

### Что сделано в v1.6.7

1. **Hybrid retrieval RRF(BM25 + bge-m3 cosine)** — `server/shared/gec_bank.py`:
   - Чистый Python BM25Okapi (k1=1.5, b=0.75, ~30 строк, без новых
     зависимостей). Индекс строится в RAM при старте (~200 мс для
     894 пар, ~6 тыс. уникальных токенов, ~2-5 МБ памяти). Disk-cache
     не нужен.
   - Токенизация без лемматизации: ловим словоформы напрямую,
     потому что грамматическая ошибка как раз в словоформе
     («стоимостей» vs «стоимости», «выполненной» vs «выполненных»).
     Если стеммировать — потеряем главный сигнал.
   - Reciprocal Rank Fusion (Cormack et al. 2009, k=60) объединяет
     ранги двух систем без подкручивания шкал.
   - Новый env `GEC_RETRIEVAL_MODE=hybrid|dense|sparse` (дефолт
     `hybrid`). `dense` — поведение v1.6.6 для отката; `sparse` —
     для ablation-тестов.
   - Latency-impact: +5-15 мс на запрос (BM25 поиск по 894 парам
     <3 мс, RRF — микросекунды). Никакого +15-25 с от GEC_TOP_K=2.

2. **Анти-галлюцинационный гард в SYSTEM_PROMPT** — `server/local/main.py`:
   - Категориальные хинты по классам ошибок согласования: число
     существительного и зависимого прилагательного/причастия;
     причастный оборот после существительного с дальним антецедентом;
     `должностного лица` (ед.ч.) vs `должностных лиц` (мн.ч.).
   - Запрет на стилистические замены: е/ё взаимозаменяемы, не
     заменять `проведенными → проведёнными`.
   - Запрет «улучшать» грамматически правильное слово: если падеж
     и число корректны — не переписывать.
   - Принцип: **лучше пропустить ошибку, чем сочинить правку**.
   - Latency-impact: ~+0.3-0.5 с (промпт длиннее на ~600 символов).

3. **Прозрачность** — `/metrics` теперь возвращает
   `few_shot_retrieval_mode` и `few_shot_bm25_terms`. Логи запуска
   показывают `mode=hybrid|dense|sparse`. На каждый запрос лог
   формата `Few-shot (hybrid): подмешиваю N пар: [...]`.

4. **Тесты** — `tests/test_gec_bank.py`:
   - `_BM25Index` (3 теста: known-doc score, unknown term, empty).
   - `_tokenize_ru` (lower, ё→е, отбрасывает пунктуацию).
   - `search_sparse` (находит лексически близкие пары, пуст при отсутствии overlap).
   - `search_hybrid` (RRF top-2, fallback на dense без BM25, пустой банк).
   - Регрессионный тест на длинном админ-входе (синтетический банк, hybrid → правильная пара top-1).

## v1.6.8 — Откат раздутого SYSTEM_PROMPT + серверный фильтр ё-замен

**Стратегия:** запрет соблюдается там, где соблюдение надёжно — на
уровне сервера, после генерации. Промпт сжимаем обратно к v1.6.6
базе, но сохраняем ОДИН компактный хинт про причастные обороты —
именно он дал +1 точную правку в v1.6.7.

### Что сделано

1. **SYSTEM_PROMPT сжат с 2680 до 1631 символа** (-1050 chars,
   -250 токенов, -8-10 с latency на T-lite на CPU).
   Сохранена единственная компактная строка о согласовании:
   *«согласование — однородные члены и причастные обороты в одном
   роде, числе и падеже с главным словом, даже если оно стоит за
   несколько слов»*. Эта одна строка и дала прирост в v1.6.7,
   остальной балласт убран.

2. **Серверный фильтр стилистических ё-замен** —
   `_drop_eyo_substitutions(text, raw_text)` в `server/local/main.py`:
   - Распознаёт пункты CHANGES, где `before` и `after` отличаются
     ИСКЛЮЧИТЕЛЬНО подменой ё↔е (или Ё↔Е): `проведенными ↔
     проведёнными`, `повлекших ↔ повлёкших`, `Тёркин ↔ Теркин`.
   - Удаляет такой пункт из `===CHANGES===`.
   - Откатывает подмену в `===CORRECTED===`, восстанавливая
     оригинальное написание из `raw_text`.
   - Срабатывает только если `before` есть в `raw_text` (т.е. правка
     реально была применена), не ломает редкие случаи с именами.
   - Применяется ДО `_drop_changes_not_in_text` в pipeline:
     ```python
     result = _drop_eyo_substitutions(result, raw_text)
     result = _drop_changes_not_in_text(result, raw_text)
     ```

3. **Тесты** — `tests/test_servers_smoke.py`:
   - `_is_eyo_only_substitution` — 9 кейсов (включая ложно-положительные).
   - `_drop_eyo_substitutions` — 6 кейсов (полная замена, частичная,

## v1.6.8 — прод-валидация и обнаруженные проблемы

**Прод-тест 5 мая 2026, ext, T-lite-it-2.1:q4_K_M, КС-2 текст:**

| Запуск | Latency |
|---|---|
| v1.6.7 (cold) | 87 с |
| v1.6.8 cold (после рестарта, 1-й запрос) | 100 с |
| v1.6.8 warm run1 (повтор 5 мин позже) | 96 с |
| v1.6.8 warm run2 (back-to-back) | **79 с** (server dur=77.9 с) |

Warm latency v1.6.8 = **79 с**, на 8 с быстрее v1.6.7. Сжатие
SYSTEM_PROMPT с 2680 до 1631 chars дало эффект, как и обещал.
Cold ~100 с — артефакт прогрева Ollama (kv-cache переинициализация
при разном `num_ctx`), это отдельный диагноз.

**Точность 2/4 стабильна между запусками:** число+причастие в
«стоимостей выполненной» и `Подразделения→Подразделению`. Между
run1 и run2 при этом CHANGES кардинально разные (run1: 1 detailed
compound пункт; run2: 3 diff-реконструированных «без точной причины»).
Это симптом недетерминированности модели (вероятно `temperature>0` в
Ollama options).

**Открытие — bypass `_drop_eyo_substitutions`:**

В run1 модель отдала **compound quote**:
```
«повлекших риски причинения ущерба Подразделения»
→ «повлёкших риски причинения ущерба Подразделению»
```

Внутри ОДНОЙ цитаты — и ё-подмена (повлекших→повлёкших), и
падежная (Подразделения→Подразделению). `_drop_eyo_substitutions`
проверяет «отличается ли before от after ТОЛЬКО ё↔е» — здесь нет,
поэтому фильтр НЕ срабатывает, и в CORRECTED остаётся «повлёкших».

**Подтверждено: модель «не указала причину» в run2** — все 3 пункта
diff-реконструированы, потому что все исходные пункты модели
отфильтрованы (`_drop_changes_not_in_text` дропнул их за неполные
цитаты или галлюцинацию).

## v1.6.9 — Char-level откат ё→е + восстановление прецедента + детерминированность RRF

**Стратегия:** закрываем bypass пост-обработкой CORRECTED ПО СИМВОЛАМ
через difflib (независимо от того, как модель упаковала changes), и
возвращаем компактный конкретный пример «актов … не предусмотренных»
в SYSTEM_PROMPT — он закрывает регресс точности с v1.6.7→v1.6.8.

### Что сделано

1. **`_undo_eyo_in_text(corrected, raw_text)`** в `server/local/main.py`:
   - Выравнивает `raw_text` и `corrected` посимвольно через
     `difflib.SequenceMatcher`.
   - Для каждого `replace`-сегмента с одинаковой длиной с обеих сторон
     посимвольно проверяет: `corrected[j] == 'ё'` И `raw[i] == 'е'` →
     откат к `'е'`. Аналогично для `Ё/Е`.
   - Сегменты разной длины не трогаем — это места реальных правок
     (вставки/удаления символов).
   - Реальная буква ё в raw_text сохраняется (имена типа «Тёркин»).
2. **`_undo_eyo_in_corrected_block(text, raw_text)`** —
   обёртка, применяющая `_undo_eyo_in_text` только к блоку
   `===CORRECTED===` в полном ответе модели, не трогая
   `===CHANGES===`.
3. **Pipeline в suggest():** char-level откат вызывается
   ПОСЛЕ `_drop_eyo_substitutions` (line-level фильтр чистых ё-замен)
   и ДО `_drop_changes_not_in_text` (валидация цитат). Так char-level
   закрывает то, что line-level пропустил из-за compound-цитат.
4. **Восстановлен компактный пример в SYSTEM_PROMPT:**
   *«согласование — однородные члены и причастные обороты в одном
   роде, числе и падеже с главным словом, даже если оно стоит за
   несколько слов («актов, …, не предусмотренных», не
   «предусмотренной»)»* (+55 chars vs v1.6.8). Целевая правка:
   `не предусмотренной → не предусмотренных` (потерянная в v1.6.8).
5. **Детерминированный tie-break в RRF** (`server/shared/gec_bank.py`):
   - Замена `for idx in candidates: ...` → `for idx in sorted(candidates)`.
   - Замена `fused.sort(key=lambda x: x[0], reverse=True)` →
     `fused.sort(key=lambda x: (-x[0], x[1]))`.
   - При равном RRF-скоре теперь стабильно выигрывает пара с
     меньшим индексом в банке. Закрывает наблюдение из v1.6.7→v1.6.8
     (одинаковый текст после рестарта возвращал разные top-1).
6. **Тесты** — 9 новых:
   - `_undo_eyo_in_text`: 7 кейсов (простой, compound bypass, имя
     с ё в raw, нет ё в corrected, верхний регистр, пустой raw).
   - `_undo_eyo_in_corrected_block`: 2 кейса (полный pipeline,
     malformed input).
   - `test_search_hybrid_deterministic_tie_break`: 5 запусков
     одного query, проверка стабильности порядка.
   - Всего 101 ✓ (было 91).

| Параметр | v1.6.8 (factual) | v1.6.9 (прогноз) |
|---|---|---|
| Точные правки | 2/4 | **2-3/4** (вернётся `не предусмотренной`) |
| Галлюцинации | 1 (Подразделению) + 0-1 ё в compound bypass | **0-1** (ё закрыт; Подразделению остаётся) |
