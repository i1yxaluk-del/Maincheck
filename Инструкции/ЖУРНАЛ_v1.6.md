# Журнал v1.6 — Retrieval-augmented few-shot для русского GEC

## Контекст

После ряда серверных фиксов v1.5.8–v1.5.11 (терминатор `===END===`, фильтр
«…»-цитат, валидация «было», реконструкция CHANGES из diff) оставалась
корневая проблема: **ни одна из 11 моделей пула не справляется с
структурной пунктуацией длинных юридических конструкций** (эталонный
текст Росгвардии, 4 известные ошибки обособления — 0-2 из 4 находятся).

Первоначальная гипотеза (см. `АНАЛИЗ_МОДЕЛЕЙ_2026_05.md`): перейти
на специализированный GEC-корректор — SAGE FRED-T5 от ai-forever.

**PoC опроверг гипотезу.** На тексте Росгвардии (30 апреля 2026):

| Модель | Латентность | Запятые найдены | Галлюцинации |
|---|---|---|---|
| `sage-fredt5-distilled-95m` (95M) | 3.2 с | 0 / 3 | «2025» → «2015», пустая «» |
| `sage-fredt5-large` (1.7B) | 22.5 с | 0 / 3 | «2025» → «2015», «ТопСервис» → «Топ-Сервис» |
| `sage-mt5-large` (1.2B) | 49 с | 0 / 3 | «2025» → «2015» |
| `sage-m2m100-1.2B` (1.2B) | 46.5 с | 0 / 3 | — (но и правок нет) |

Выводы:
1. SAGE обучена на типо- и орфо-ошибках из Wikipedia/видео-транскриптов,
   а не на структурную пунктуацию обособления. Другая задача.
2. SAGE стабильно галлюцинирует числа («2025 год» → «2015 год»).
   Для юр.документа — критичная ошибка.
3. F1 paper-метрик (60 %) получены на RUSpellRU, а не на нашем домене.
   Academic benchmark ≠ prod.

## Новая гипотеза (v1.6)

Проверил Sorokin & Nasyrova (BEA @ ACL 2025, LORuGEC paper). Их
эмпирические цифры на русском GEC:
- 0-shot LLM (T-lite / YandexGPT): **~55 % F0.5** (то что у нас сейчас)
- 5-shot LLM + GECToR retrieval: **83 % F0.5 — SOTA**
- Fine-tune seq2seq: 65–75 % F0.5 (хуже retrieval-augmented)

Retrieval лучше fine-tune. Ещё и почти бесплатно.

## Архитектура v1.6 Этап 1 (реализована)

```
ПОТОК:
    request (raw_text + context)
        ↓
    _rag_context(raw_text)           # старый RAG, без изменений
        ↓
    [NEW] _gec_bank.search(raw_text, top_k=3)  # FAISS-like в numpy
        ↓ [top-3 похожих пар из банка]
    [NEW] build_few_shot_messages(   # system + N × (user, assistant) + user
              SYSTEM_PROMPT, user_msg, examples
          )
        ↓
    call_ollama(messages)            # тот же T-lite-it-2.1
        ↓
    ===CORRECTED=== / ===CHANGES===  # тот же формат
        ↓
    _drop_idempotent_changes  ← оставили 1.5.11 как есть
    _drop_changes_not_in_text ← оставили 1.5.11 как есть
    _rebuild_changes_from_diff ← оставили 1.5.11 как есть
        ↓
    client
```

### Файлы

- `server/shared/gec_bank.py` — новый модуль (`GecPair`, `GecBank`,

- `server/shared/gec_seed/gec_bank.jsonl` — seed-банк 288 пар из LORuGEC,
  сбалансирован по 48 правилам (≤ 6 примеров на правило). Размещён
  в `shared/gec_seed/`, а не `local/data/`, потому что `data/` глобально
  в `.gitignore`.
- `server/local/main.py` — добавлены env-флаги `USE_FEW_SHOT`,
  `GEC_BANK_FILES`, `GEC_TOP_K`, интеграция в `/suggest`,
  поля в `/health` и `/metrics`.
- `server/local/.env.example` — секция Few-shot retrieval с инструкцией
  и ссылкой на исходник.
- `tests/test_gec_bank.py` — 8 тестов (load/skip/search/build-messages/
  seed-sanity).

### Эмбеддер

Переиспользуем RAG-эмбеддер (если `RAG_ENABLED=true`) — один
`OllamaEmbedder(nomic-embed-text)` на оба индекса. Если RAG выключен,
создаём свой Ollama-эмбеддер; если Ollama недоступен — падаем
в `HashingEmbedder(dim=1024)` (лексический fallback без сети,
качество ниже, но сервер не ломается).

## Источник seed-банка и лицензирование

- Данные: LORuGEC (Sorokin & Nasyrova 2025, BEA @ ACL 2025),
  https://github.com/ReginaNasyrova/LORuGEC
- Формат исходника: XLSX, 961 строка, 48 правил,
  колонки «Initial sentence» / «Correct sentence» / «The rule» / …
- Обработка (см. `/tmp/build_seed_bank.py`, коммитить не нужно):
  - оставлены только пары, где `Are both sentences the same? == No`
  - детокенизация (убран пробел перед пунктуацией)
  - баланс `≤ 6 пар на правило` (чтобы банк не был перекошен)
  - 288 пар на выходе
- Цитирование обязательно (описано в `.env.example` и docstring модуля).

## Что НЕ сделано в этом релизе (deferred)

1. **Миграция на llama.cpp** — отдельная v1.6.1. Ortogonal от retrieval:
   retrieval уже даёт +20–30 % качества, llama.cpp добавит −35 %
   латентности. Сперва смотрим на качество, потом ускоряем.
2. **Интеграция ведомственных документов в банк** — точка расширения
   готова (добавить путь в `GEC_BANK_FILES` → `build_index`). Ждём
   корпус от заказчика.
3. **Бенчмарк на LORuGEC-test (1945 пар)** — скрипт отдельно, не
   блокирует PR. Acceptance criteria по paper: F0.5 ≥ 70 % (vs
   ~55 % в 0-shot).
4. **Проверка на Росгвардии с USE_FEW_SHOT=true** — требует реального
   Ollama на прод-машине, делается после мержа PR.

## Ожидаемые acceptance criteria

На момент релиза (acceptance на проде):

1. `USE_FEW_SHOT=false` — **побайтово** то же поведение, что в v1.5.11.
   Гарантируется: код пути few-shot изолирован, `messages` строится
   старой веткой.
2. `USE_FEW_SHOT=true` — на тексте Росгвардии: **≥ 3 из 4**
   эталонных запятых обособления находятся. (Сейчас 0–2.)
3. Warm-латентность — без регрессий. 3 примера × ~150 токенов =
   +450 tokens в промпте → при `num_ctx=2048` запас остаётся,
   `num_predict` не меняется, ожидаем +3…5 с к warm (45 → 48–50 с).
4. Формат `===CORRECTED===/===CHANGES===/===END===` — стабилен.
   Каждый из 3 assistant-примеров в истории демонстрирует правильный
   формат, модель имитирует.
5. Никаких новых галлюцинаций. Все предыдущие защиты
   (`_drop_changes_not_in_text`, `_rebuild_changes_from_diff`) активны.

# Журнал v1.6.1 (5 мая 2026) — диагностика NUMA + расширение GEC-банка

## NUMA-фикс (главная победа сессии)

При тестировании 8B (`t-tech/T-lite-it-2.1`) и 4B (`Vikhrmodels/QVikhr-3-4B`)
на прод-сервере latency была катастрофической — простое `ollama run "Привет"`
занимало **1м37с** на 4B-модели, а `/suggest` упирался в таймауты 300-900 с
даже при 0-shot.

`ollama run --verbose` показал:
- `prompt eval rate`: **0.66 tok/s** (ожидаемо: 30-60)
- `eval rate`: **0.07 tok/s** (ожидаемо: 5-7)

Корень: VMware-виртуалка с 2 NUMA-нодами по 16 ядер/16 ГБ; Ollama в systemd
запущена через `numactl --cpunodebind=0 --membind=0` — половина железа
отрезана, плюс жёсткий NUMA-bind в гостевой ОС конфликтует с расписанием
vCPU гипервизором.

**Фикс — заменить `/etc/systemd/system/ollama.service.d/override.conf`:**

```ini
[Service]
ExecStart=
ExecStart=/usr/local/bin/ollama serve
Environment="OLLAMA_KEEP_ALIVE=24h"
Environment="OLLAMA_NUM_PARALLEL=1"
```

```bash
sudo systemctl daemon-reload
sudo systemctl restart ollama
```

После фикса:
- `prompt eval rate` 0.66 → **58 tok/s** (88×)
- `eval rate` 0.07 → **5.29 tok/s** (75×, для 4B); 9.22 tok/s для 8B
- `ollama run "Привет"` 113 с → **1.79 с**

## Latency после фикса (T-lite 8B + retrieval)

| Тест | Latency | Найдено эталонных ошибок (4 шт.) |
|---|---|---|
| 0-shot | 74 с | 4/4 (2 точно + 2 валидной альтернативой) |
| 1-shot (top_k=1) | 75 с | 4/4 |
| 3-shot (top_k=3) | — | не тестировали (1-shot достаточно) |

**Цель «70-80 с с лучшим качеством» достигнута на T-lite 8B без llama.cpp.**

## Расширение GEC-банка

Существующий `gec_bank.jsonl` — 288 пар (по 6 примеров на правило × 48 правил).
В тесте Росгвардии retrieval не находил релевантных пар на ошибку
`должностного лиц → должностных лиц` (Grammar/число), потому что в банке
было только 24 grammar-пары на 4 правила.

**Расширение через `tools/build_gec_bank/build.py`:** парсим
полный LORuGEC.xlsx (960 пар) → `gec_bank_extended.jsonl` (639 новых пар,
не пересекаются с базовым банком). Итого после подключения двух файлов:

| Раздел | Базовый | Расширенный | Итого |
|---|---|---|---|
| Spelling | 150 | 317 | 467 |
| Punctuation | 102 | 235 | 337 |
| Grammar | 24 | 55 | 79 |
| Semantics | 12 | 32 | 44 |
| **Всего** | **288** | **639** | **927** |

**Latency-импакт расширения банка: 0%.** Размер банка не влияет на /suggest
runtime — мы достаём top_k (=1) ближайших примеров из любого по размеру
пула. Изменяется только время первичной индексации (linear по объёму, потом
disk-cache из v1.6.0).
